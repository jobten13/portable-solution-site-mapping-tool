## 2. THE PER-STEP WORKFLOW (settled by hard experience — do not deviate)

For every step of every effort:

1. **Plan request** → Coder (Ask mode). Read-only. The plan must name EVERY file it will touch (standing rule, origin: Step 4 digest drift — see §6). Plans propose; they do not execute.
2. **Developer review/approval** — Claude summarizes the plan, gives reads on flags with recommendations, drafts an approval message. Developer decides. Approval messages restate any amendments explicitly.
3. **Build** → Coder (developer flips to Agent mode, sends the approval / "Execute Step N as approved"). Coder reports the full diff. **Does not commit.**
4. **Independent audit** → Auditor (separate chat, Ask mode, `/auditor` prefix). Claude drafts the audit checklist — scope, invariants, accuracy, no stray state, plus step-specific items. Pass/fail per item with line references.
5. **Developer visual test** where anything renders — Claude provides a concrete checklist. **The commit message is drafted ONLY AFTER the visual test result comes back** (rule origin: a commit once ran before the eyeball; both parties agreed to separate the exchanges).
6. **Commit** — developer runs it; Claude proposes the message. Messages only claim what is already true (rule origin: a commit message once referenced a formula "preserved in Notes" that hadn't landed yet — required a follow-up docs commit).
7. **Docs current** — `PSMT_Project_Notes.md` is updated in the same commit as code, or immediately after as its own docs commit. README/Quickstart are deliberately BATCHED — synced only at the next version bump, per an explicit logged decision. Do not update them per-change.

Other standing rules, with origins:
- **One thing at a time.** Do not bundle unrelated work. Flag, don't fix, anything outside the current step. (The developer has explicitly corrected drift on this — mid-task side quests get parked.)
- **Verify before claiming.** Never assert codebase facts from memory. If unsure, write a read-only Cursor check. Never contradict the developer's visual observations — investigate them.
- **Never filter data.** Complete lists, every item, when passing reports or writing instructions from findings.
- **Design decisions belong to the developer.** Present options, state a recommendation, never pick. Once decided, do not relitigate.
- **Simplicity over cleverness.** This is a field tool for stressed users; planning-tool precision ("right area code"), not over-engineering.
- **Fail-closed bias** for anything gating field-visible content.
- **Provenance discipline:** never invent data; unconfirmed figures ship marked unconfirmed with their source chain; conflicts are recorded, not adjudicated, unless the developer resolves them with source evidence.
